● Read the brief and the code it points at. Three things in the brief the code
  contradicts — worth correcting first, because they change the answers.

  1. "A new Python route needs no gateway change" is false for this feature. The
  /api/ml/* wildcard is registered inside the protected group
  (go-gateway/main.go:56-57), so every /api/ml/* route inherits RequireAuth —
  and RequireAuth reads a cookie named token (internal/middleware/auth.go:14),
  not an Authorization header. There is no bearer path anywhere in this stack
  today. An external caller has neither a cookie nor a way to send one. This
  feature touches main.go no matter which design wins; the only open question is
  how much.

  2. /api/ml/predict has no ownership check at all. It takes model_key verbatim
  and downloads it with the service key (sklearn_router.py:87-95). Any logged-in
  user holding any model_key can run any user's model. Being browser-only has
  been hiding that. Whatever we expose must not inherit it.

  3. There is no "the trained model" in the schema. MlModel carries no artifact
  pointer. The bytes live in Experiment.modelFilePath (Experiment.java:46), and
  a model has many experiments. "Serve model X" is ambiguous until we say which
  run.

  One piece of good news for the budget: ddl-auto: update (application.yml:11)
  means a new JPA entity creates its own table on boot. No migration file, no
  hand-written SQL.

  ---

  ❓ Q1 - Who the credential belongs to, and what revocation has to undo: The
  brief frames this as trainer-vs-delegate. I think that's the wrong axis — it's
  a docs question, not a code question. The code question is scope: does a
  credential authorize the account (everything that user owns, forever) or one 
  model?

  If it authorizes the account, handing it to a contractor hands them every
  model you will ever train, and revoking it breaks your own integrations too.
  If it authorizes one model, "delegate" and "my own script" become the same
  case, and revocation is precise.

  ➡️ Credentials belong to a user but are scoped to a single model, and a user
  can hold several. Delegation is then just "you hand someone the string,"
  needing no extra machinery, and the brief's first open question dissolves.

  ---

  ❓ Q2 - What the credential is, and what we store: Three shapes. (a) Opaque
  random key, hashed at rest. (b) A long-lived JWT signed with the existing
  JWT_SECRET — zero storage, but unrevocable without a blocklist table, which is
  the same table as (a) with worse properties. (c) HMAC request signing —
  replay-resistant, and far more than a day of work on both ends.

  For (a): the secret is 256 bits of real entropy, not a human password, so
  bcrypt buys nothing. Store sha256(key) under a unique index and verify with
  one indexed lookup. Keep a plaintext display prefix (dlp_a3f9…) so the UI can
  tell keys apart, and show the full key exactly once at creation.

  ➡️ (a). It is the only one of the three where "revoke" is a single DELETE and
  the plaintext secret is genuinely not recoverable from our database.

  ---

  ❓ Q3 - Which service authenticates the external caller: This is the real
  architectural fork, and I want you to push back on my answer.

  Gateway verifies — a new public route group calls Java to check the key, then
  sets X-User-ID and proxies to Python. Keeps the invariant every downstream
  ownership check already assumes: X-User-ID is set by the gateway and is always
  trustworthy. Cost: the gateway makes a DB-backed HTTP call per request, and
  main.go:37 currently brags about doing no DB work.

  Python verifies — the gateway just proxies a public path through, and Python
  asks Java about the key, exactly as _fetch_owned_dataset already asks Java
  about datasets. Keeps the gateway dumb. Cost: two trust boundaries instead of
  one, and Python gains a route where X-User-ID is self-derived rather than
  gateway-asserted — the invariant splinters, and the next person to add a route
  has to know which kind they're writing.

  ➡️ Gateway verifies. One trust boundary is worth one HTTP hop, and CLAUDE.md
  already says the gateway is the contract. The per-request Java call with no
  cache is a named production gap, not a design flaw at this budget.

  ---

  ❓ Q4 - What the caller names in the URL: Given fact 3 above, three
  candidates. model_key — the raw storage path; leaks internals, can't be
  revoked, and is exactly the hole in fact 2. Experiment id — precise, but the
  user has never seen one and the UI doesn't surface it. Model id — the thing
  that appears in MyModels.tsx, resolved server-side to the latest completed
  experiment.

  ➡️ POST /api/serve/{modelId}/predict, resolved server-side to the newest
  completed experiment, with the key required to match that model id. The model
  id in the path is redundant with a model-scoped key, and that redundancy is
  what lets us give a clean "no such model" vs "not your model" answer. The cost
  is that retraining silently changes what an external caller gets — pinned
  versions are a deliberate cut, and it goes in the docs.

  ❓ Q5 - What actually crosses the gateway→Python boundary (this is your Q4,
  answered): You're right, and I'll drop my recommendation. The model id in the
  path is redundant: if the key resolves to exactly one model, POST 
  /api/serve/predict is the whole surface, and the "right key, wrong model"
  error case the brief asks about stops existing by construction rather than
  needing a handler.

  But that forces a consequence. If RequireAPIKey resolves key→model at the
  gateway, Python must be told the model — otherwise the raw key has to travel
  to Python and get re-verified, and we're back to two verification points. So
  the gateway sets X-Model-ID next to X-User-ID, and your two Python entrypoints
  differ only in where the id comes from — path for the browser gate, header
  for the API gate — before converging on _run_prediction. That is exactly the
  shape you sketched.

  Two riders. First, the residual risk of dropping the id from the URL is a user
  pasting the wrong key into the wrong script and getting confident predictions
  from the wrong model — silent wrong answers, the worst failure mode there is.
  Cheap fix: the response echoes model_id and the model title, so the mistake
  is visible without a required path param.

  Second, hygiene: proxy.To calls Header.Set("X-User-ID", …) only when userID !=
  "" — it never deletes an inbound one. Today that's masked because every
  proxied route sets it. Your new group makes it load-bearing, so the proxy
  should unconditionally Del both X-User-ID and X-Model-ID before setting them,
  and strip Authorization so the raw key never travels deeper than the gateway.

  ➡️ Flat /api/serve/predict; gateway sets X-User-ID + X-Model-ID; proxy deletes
  both inbound and strips Authorization; response echoes the model identity.

  ❓ Q11 - The Java verify contract, and what happens when Java is down: POST

  ➡️ POST with key in body, /internal/api-keys/verify, 2s timeout, no cache, 503
  when Java is unreachable and 401 only on an actual miss.

      299  **Gateway injects X-User-ID header** — JWT is validated once a
           t the gateway; downstream services read `X-User-ID` from the h
           eader instead of parsing JWT themselves. Java and Python never
            see the raw token.
      300  
      301 +**API keys are verified at the gateway, not in Python** — `Req
          +uireAPIKey` resolves the key to its owner and its one model by
          + asking Java, then sets `X-User-ID` and `X-Model-ID` for downs
          +tream services. This keeps a single meaning for `X-User-ID` ev
          +erywhere: always gateway-asserted, never self-declared, so eve
          +ry ownership check already in Java and Python keeps working un
          +changed. The cost is that external predictions now need Java o
          +n the request path — recorded in `planning/decisions.md`.     
      302 +                                                              
      303 +**A key authorizes one model, not one account** — handing a ke
          +y to a contractor cannot leak the rest of your models, and rev
          +oking it cannot break your other integrations. Keys are 32 byt
          +es of `SecureRandom` stored as SHA-256 under a unique index; t
          +he plaintext exists only in the response that creates it.     
      304 +                                                              
      305 +**Deployment is an explicit pointer** — `ml_models.deployed_ex
          +periment_id` names which training run answers requests. It use
          +d to be whichever completed run sorted first, which meant retr
          +aining silently changed what callers got. The first completed 
          +run auto-deploys so nothing regressed; every change after that
          + is a button press.

  Candidates examined and excluded

  Recorded because a bare "nothing found" is not reviewable.

  1. Path injection into the Java URL via model_id — excluded (no proven impact)

  python-ml-service/prediction.py:29 interpolates model_id into a URL without
  validating it as a UUID:

  f"{JAVA_SERVICE_URL}/api/models/{model_id}/deployment"

  Through the external door this is not reachable: X-Model-ID is set by the
  gateway from Java's verify response, so it is always a UUID read out of the
  database. Through the browser door (/api/ml/models/{model_id}/predict) the
  value is caller-controlled and typed str, so ../ sequences can reach the URL
  builder.

  Excluded because no privilege is gained. X-User-ID on that request is the
  caller's own gateway-asserted identity, and every /api/* endpoint reachable by
  traversal is already reachable by that same caller through the gateway with
  the same identity. The only path outside /api/ is /internal/api-keys/verify,
  which is POST-only while this call is a GET. The authority component cannot be
  influenced, so this controls the path only — excluded under the SSRF
  precedent and the input-validation exclusion.

  Still worth fixing as hardening: typing the parameter model_id: UUID in
  sklearn_router.py closes it at the boundary and costs one word.

  2. Unauthenticated /internal/api-keys/verify — excluded (not newly introduced)

  The platform could train a useful model and then strand it. A trained model

  ## Design

  Full reasoning in `planning/decisions.md` (13 numbered decisions, each naming
  what
  was rejected). `planning/spec.md` is what got built. The load-bearing choices:

  **Two doors, one implementation.** The browser keeps its cookie path; the
  outside
  world gets a key path. Both prove identity at the gateway and converge on a
  single
  `run_prediction()` in Python, so the ownership rule exists in exactly one
  place.

  ```
  browser  ──cookie──▶  gateway ─RequireAuth───▶  POST
  /api/ml/models/{id}/predict ─┐

    ├─▶ run_prediction()
  script   ─X-API-Key─▶  gateway ─RequireAPIKey─▶  POST /api/serve/predict
     ─┘
                            │
                            └──▶ java  POST /internal/api-keys/verify
  ```

  **A key authorizes one model, not one account.** Handing a key to a contractor
  cannot leak the rest of your models, and revoking it cannot break your other
  integrations. This also dissolves a whole error case: "right credentials,
  wrong
  model" cannot happen, so there is no status code for it.

  **The key alone names the model.** `/api/serve/predict` takes no model id — a
  path
  parameter would be redundant with the key and could only ever disagree with
  it. The
  response echoes `model_id` and `model_title` so the wrong key in the wrong
  script
  shows up as a wrong title rather than as confident predictions from a model
  you did
  not mean.

  **Verification happens at the gateway, not in Python.** `RequireAPIKey`
  mirrors
  `RequireAuth`: it resolves the key by asking Java, then sets `X-User-ID` and
  `X-Model-ID` downstream. This preserves a single meaning for `X-User-ID`
  everywhere —
  always gateway-asserted, never self-declared — so every existing ownership
  check in
  Java and Python keeps working untouched. The cost is real and recorded:
  external
  predictions now need Java on the request path, measured at ~0.57s per call,
  almost
  entirely the two Java round trips.

  **`503`, not `401`, when the verifier is down.** With Java unreachable the
  gateway
  cannot tell a good key from a bad one. Answering `401` asserts something it
  does not
  know and tells the caller to rotate a key that was never bad — automate that
  and an
  outage becomes a stampede of key regeneration.

  **Deployment is an explicit pointer.** `ml_models.deployed_experiment_id`
  replaces
  an implicit rule (`Process.tsx` used whichever completed run sorted first),
  which
  would have meant retraining silently changing what external callers receive.
  The
  first completed run auto-deploys so nothing regressed; every change after that
  is a
  button press.

  **This PR removes a vulnerability rather than adding one.** The deleted
  `POST /api/ml/predict` accepted a client-supplied `model_key` and passed it to
  `joblib.load` — pickle deserialization — after fetching it with the Supabase
  service
  key, with **no ownership check at all**. Any authenticated user holding any
  object
  path could load another user's artifact. It is deleted, not patched; the
  server now

  - `proxy.To` now `Del`s `X-User-ID`, `X-Model-ID` and `X-API-Key` before
  setting the

  - The raw key is stripped at the gateway and never reaches Python.

    bcrypt: bcrypt exists to slow guessing of low-entropy passwords, and there
  is no
    guess space here to protect.
  - The key travels to Java in a POST body, never a URL path, so it stays out of
  access
    logs.

  preflight. A
